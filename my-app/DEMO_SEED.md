# Demo database seed

Run commands from `my-app` after `npm ci`. The database must already have the existing application schema and migrations. This script does not create or change the schema, run migrations, or deploy the application.

The seed uses the existing Prisma 7 configuration (`prisma7.config.ts`), generated client and PostgreSQL driver adapter. Prisma 7's `migrations.seed` setting runs only through an explicit seed command. See the [Prisma seed command reference](https://docs.prisma.io/docs/cli/v7/db/seed).

## Commands (PowerShell)

Preview the exact fixtures without connecting to a database:

```powershell
npm.cmd run seed:demo -- --dry-run
```

For a local database, set its connection string for this PowerShell session (replace the example credentials and database name):

```powershell
$env:SEED_DATABASE_URL = 'postgresql://LOCAL_USER:LOCAL_PASSWORD@127.0.0.1:5432/smart_order_demo'
npm.cmd run seed:demo
Remove-Item Env:SEED_DATABASE_URL
```

`SEED_DATABASE_URL` overrides `DATABASE_URL` only inside the seed. Without an override, the seed uses `DATABASE_URL` from the shell or `.env`; `.env.local` is not loaded. Non-local hosts are refused by default. A localhost connection forwarded to a remote database is still remote in practice: use only a known local demo database for the local command.

To manually seed the PostgreSQL database used by your Vercel deployment later, copy that database's connection string from your provider into a private environment variable. Use the database connection string, not the Vercel website URL. Inspect the target before running:

```powershell
$env:SEED_DATABASE_URL = 'YOUR_VERCEL_PRODUCTION_POSTGRESQL_CONNECTION_STRING'
npm.cmd run seed:demo -- --allow-remote
Remove-Item Env:SEED_DATABASE_URL
```

Use `npm.cmd` in PowerShell so script flags reach Prisma correctly. In Bash or other non-Windows shells, use `npm` instead. No production seed or deployment is automatic. Do not commit connection strings or keep new login passwords in shared build logs.

### Orders

Orders are first allocated using the application's actual allocation algorithm and stock deduction helper. Completed/cancelled examples then use the existing completion/cancellation helpers in the same transaction. No pending order is inserted because customer placement normally creates an allocated order.

| --- | --- | --- | --- | --- | --- |
| 2026-09-01 09:00 | Nimal | 6.9344, 79.8428 | Milk powder ×5; water bottle ×2 | ALLOCATED | Nugegoda |
| 2026-09-02 10:30 | Ishara | 7.2906, 80.6337 | Tea ×2; red rice ×3 | COMPLETED | Kandy City |
| 2026-09-03 14:00 | Nimal | 6.0269, 80.2170 | Coconut milk ×2; herbal soap ×4 | CANCELLED | Galle Fort |

The first example demonstrates allocation beyond the nearest branch: Colombo Fort cannot supply five milk powders and two bottles, so eligible branches are scored using distance and active workload. To demonstrate another checkout, use the same quantities at Colombo Fort's coordinates; on an otherwise fresh demo database, Nugegoda remains the best eligible branch. Existing stock, workloads, and branch locations can change the allocation result. Completed orders keep their stock deduction; cancelled orders restore it.

## Duplicate prevention and preservation

- Products/branches are matched by exact demo names. Ambiguous duplicate names abort the transaction rather than selecting an arbitrary record. Their existing prices and coordinates are preserved.
- Customers are matched by the schema's unique email. An incompatible existing name, role or password format aborts the seed; accounts are not promoted or overwritten.
- Inventory uses the existing unique `(branchId, productId)` constraint. Missing inventory is created only when its branch or product is newly created in that run. Later stock changes or inventory removals are preserved; rerunning does not replenish stock.
- Orders/inquiries are identified by customer ID and fixed creation timestamp, irrespective of current status. Reruns preserve lifecycle changes and staff replies and do not deduct order stock again. Editing these identifying timestamps/emails/names or manually deleting demo orders can prevent matching; do not use reseeding to restore such altered examples.
- A PostgreSQL transaction-scoped advisory lock serializes seed runs. `ReadCommitted` ensures a waiting run sees its predecessor's committed records. The entire seed is atomic; an allocation failure, account collision, or database error rolls it back. Concurrent application stock updates still use the normal conditional deduction rules.
- No real records are deleted. There is no reset, drop, truncate, migration, or fixed numeric ID assignment. Only newly created demo orders are transitioned. The script prints actual creation counts after commit.

## Verification

```powershell
npm run test:seed
node --test tests/*.test.mjs
python -m unittest discover -s ai/tests -v
npm run build
```

Seed tests use a transactional in-memory store and the actual application allocation, deduction, completion and cancellation helpers. They check password hashes, stock consistency, idempotence, preservation, target guards and rollback failures. They do not replace a PostgreSQL integration run. If a safe local database is available, run the local seed twice: the second run should report zero new records and leave stock/passwords/statuses unchanged. The preview command never connects to a database.
